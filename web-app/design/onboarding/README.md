# OHMI onboarding

Mode: Operate / Read. Design variance5, motion3, density4. This additive guided tour preserves the existing mint/charcoal workspace, Geist typography, canonical pixel mascot, semantic tokens, house buttons and Radix dialog mechanics. The ten-step scope comes from the owner-provided onboarding brief. Marketing-page design rules do not apply to this product flow.

## Behavior and persistence

- Newly registered authenticated users receive an optional invitation on entering Dashboard after their workspace loads. Start Tour, Maybe Later, close and Escape are available. The invitation is claimed atomically **before** display, so dismissal, skipping, starting or completion cannot cause another automatic invitation on another browser/device.
- `ohmi_profiles.onboarding_invited_at` stores the claim. No user-facing claims rely on localStorage, browser clock, profile creation time, editable user metadata, a query flag, or first-device visit. The database compares trusted `auth.users.created_at` against a single private, server-timestamped rollout boundary. Accounts created before activation are excluded without backfilling or overwriting their profile/student data. Anonymous and signed-out users are excluded.
- A narrow security-invoker public RPC calls a fixed-search-path private helper that checks auth.uid(), reads the trusted Auth registration timestamp, then performs a conditional one-time update. Existing profile ownership RLS remains unchanged. Browser roles cannot reset the timestamp, access the private rollout table, or claim for a supplied user ID. No caller-selected account ID is accepted. Claims from concurrent devices serialize on the profile row.
- The authenticated same-origin POST `/app/api/onboarding/` returns only `{invite:boolean}`, with private/no-store headers. There is no GET mutation. A failed or timed-out status check fails closed: no automatic interruption. Manual replay reports a retryable error if the claim cannot be persisted. Claim state is not reset by replay.
- Settings adds a subtle Take a Tour control. Replay is available to all signed-in accounts; it visits the real Dashboard, Ask, Assignments, Checker, Guide, Playground, Library, Progress and Settings screens. Welcome and Dashboard are separate steps. The final explanation points to existing Floating OHMI controls without launching the widget.
- Next, Back, Skip, Finish, Escape and Close work. Native browser Back exits an out-of-context tour. Account-owned React state remounts on user changes; pending old-account results cannot display to a different account. The client shares its one pending claim across Strict Mode effect replay.
- The tour uses a geometric SVG mask over actual UI targets. It scrolls/positions against the actual element and falls back to a visible page heading for missing/hidden targets. Mutation/resize observers handle route readiness and layout changes, with cleanup. Modal focus stays inside the explanation card and returns to the invoking control or main content. Controls stay usable while a route loads; Skip/Close always remain available.
- Motion is limited to short explanation transitions and programmatic scrolling. OS and in-app reduced motion select static/instant behavior. The card adapts to viewport dimensions and supports the existing large-text preference.
- No tour action submits AI requests, uploads, marks lessons complete, saves Playground projects or spends provider quotas. Existing screens may load their normal private lists and capability GETs when visited. Navigation does not execute a full electrical simulation; copy accurately describes screenshot limitations and Playground's limited built-in checks.

## Release sequence and rollback

The owner brief authorizes GitHub push and Vercel release. Publish the verified frontend to the existing `codex/ohmi-web-app-pwa` branch first. Until the RPC exists, its status check fails closed. **After** Vercel reports success, apply only migration20261025141802 with Supabase CLI. This captures the real backend activation boundary after the frontend is available, excluding every pre-activation account. Verify the installed function/permissions and rerun the transactional database checks. Do not reset the cutoff on future application deployments.

Frontend rollback may retain the additive timestamp/private rollout record. Do not delete claims or move the rollout boundary: doing so could re-invite returning users. No student records need deletion for rollback.

Physical devices, Safari/Firefox, real Google registration, field performance and live AI actions were not tested. The automatic invitation is consumed before rendering; if a device closes or loses the response after a successful claim, that account may miss its one automatic invitation. Manual Take a Tour remains available, prioritizing the explicit requirement against repeat interruptions.
