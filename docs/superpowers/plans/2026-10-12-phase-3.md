# OHMI Phase 3 implementation plan

> **For agentic workers:** Use superpowers:executing-plans task-by-task. Owner explicitly approves automatic implementation, testing, and reasonable decisions without approval pauses.

**Goal:** Secure accounts, private assignment files, and persistent preferences/assignment steps without exposing session credentials to Tinkercad.

**Architecture:** A background Supabase client and validated runtime messages own privileged work. An extension Account page handles credentials and real-progress uploads; the floating panel receives safe views. Three RLS-protected tables and one private bucket support user records.

**Tech stack:** Existing WXT/React/TypeScript/Tailwind/Vitest/Playwright, pinned Supabase JS 2.117.3, Supabase CLI 2.120.0 for migrations/local verification.

**Spec:** [Phase 3 design](../specs/2026-10-12-phase-3-design.md). Fresh builder check found no important unanswered design questions.

**Accepted handoff:** owner deferred email confirmation/reset until custom SMTP and confirmed real Google login/name saving. Implementation/backend gates passed under that revised scope; details are in [Phase 3 verification](../../PHASE_3_VERIFICATION.md). Intermediate source/schema/UI slices are committed together as one verified Phase 3 change.

## Constraints and rulings

- Use only public Supabase URL/publishable key in extension configuration. Exposed privileged credentials are unused and must be rotated by owner.
- Live operations target only verified `vhmdgfydvoljzqztuxmu`; inspect existing schema/bucket/auth settings first. No destructive live operations.
- Keep demo chat, sample guide, and sample circuit distinct from student records. No AI, PDF analysis, capture, or Phase 4.
- Ruling: use `phase-3` branch in the current checkout rather than a new worktree. Changing the unpacked extension path would change the owner's callback identity. Existing Phase 2 commit remains recoverable; cost is less filesystem isolation.
- Ruling: email OTP confirmation/recovery avoids external email redirects to an unhandled Chrome identity URL. Verify callback allow list and email templates; cost is requiring OTP-enabled templates and a pasteable code.
- Existing installed extension ID remains the required identity. No replacement manifest key is generated. A public key is needed for stable distribution across machines.

## Review focus

- Content scripts must neither read trusted auth storage nor request credentials/upload authorization; forged sender/messages fail closed.
- Concurrent Google/signup/recovery operations must not overwrite PKCE/session state; cancellation is recoverable.
- Account switches must replace owner data/language and never persist demo progress or stale data to another account.
- Interrupted uploads and failed deletion must retain recoverable metadata; no orphaned object from metadata-first deletion.
- MIME/size/signature/path validation and composite ownership constraints must reject malicious cross-user input.
