# M2: local compatibility and private persistence

The owner approved local implementation, tests and an additive migration draft. No hosted migration, AI request, push or deployment was authorized or performed. The existing Playground remains the default.

## Implementation

- New `ohmi_electronics_projects` storage, separate from the legacy table. Owner-only RLS, server-owned engine pin, revision checks, immutable source provenance, bounded JSON and server timestamps. The migration is **a draft for separately approved rollout**.
- Same-origin authenticated CRUD at `/app/api/playground/projects/`. An expected-account header also prevents stale account contexts from reading/writing under changed cookies. Queries retain explicit owner filters; private responses are no-store. Stale saves/deletes and duplicate create UUIDs return 409. Missing storage returns 503 with `.dez` fallback.
- Paginated native and legacy summaries use the new account-bound API. Legacy conversion reads the owned source/revision server-side, creates a new UUID and retains its exact original project snapshot. Database checks verify source ownership/revision/snapshot and prevent later provenance changes. No legacy row is updated or deleted by conversion.
- Strict native document envelope/version, bounds, duplicate-ID, terminal, geometry, code and custom-definition validation. Metadata comes from all **791 native catalog entries / 349 types**. Variable DIP/header/connector/breadboard terminals are checked against their configurations. Unknown parts need a bounded native custom definition; unsupported data fails explicitly.
- Four-kind legacy mapping: battery plus/minus, resistor pin0/pin1, LED anode/cathode and SPDT common/a for the old two-terminal switch. Coordinates convert to mils and actual native terminal positions in all three views. Original missions/hints/completion/switch history stay in source provenance and the original save; new simulation behavior can differ.
- Private-project disclosure supports snapshot/save-copy, open, delete, pagination and legacy copies. Account unmount aborts requests and destroys the native runtime. Replacing local files/reloading clears save identity.
- Native New/Open/example/history-copy actions also change a browser session generation. Atomic capture binds a private record to generation plus native document UID. A replacement saves to a separate record, even when the opened file reuses the same UID; ordinary edits still update the selected record. Session generation is not saved in `.dez` or used for authorization.

## Limits and rollback

Hosted storage remains unavailable until its own rollout is approved. API/UI tests use a PostgREST boundary double; this phase does not claim end-to-end hosted or real local PostgREST verification. Database semantics are independently exercised in PostgreSQL. No real student records, Google consent, AI generation, physical touchscreen, Safari, hardware or full native screen-reader certification was tested. M3 AI planning and M4 final experience/release remain separate gates.

Native saves have a 1 MiB bridge/API document budget and a 1 MiB PostgreSQL JSONB-text ceiling. JSONB spacing can reject a document near that ceiling; errors retain local work and instruct `.dez` download. Large projects can use native exports. Unfinished Arduino code is preserved; saving is not a claim that it compiles or simulates successfully. Native file-save indicators are distinct from captured cloud snapshots. Technical canvas colors and comprehensive editor accessibility/polish remain M4.

The detector reports only heading-size advisories, including the inherited main heading and the local subheading; no primary finding. Existing shared PRODUCT/DESIGN metadata drift remains untouched. No application dependency, provider routing, billing or Codex hook changed.

Rollback locally by returning to the M1 checkpoint (`20aaf6e`), using the legacy Playground and exporting any native work first. The hosted migration has not been applied, so no hosted rollback is needed. A future frontend rollback must retain additive saved data; do not drop the new table to roll back a released UI. The rollback SQL files are synthetic test rehearsals, not a production teardown procedure.
